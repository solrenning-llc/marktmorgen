Depois: tsc sem erro novo, testes dos arquivos tocados (RED→GREEN se algo quebrou), `git merge-tree` limpo, um push no seu minuto e com o semáforo (ALL-236 A3/A4; MV (c); com a issue `main-vermelho` aberta, nenhum, MV (a)) e o pedido "re-review needed #N @sha10 (merge of main)". Se os dois lados forem dois desenhos incompatíveis, não escolher no escuro: registrar o trecho exato no canal e no PR, e seguir com os outros.

(c) **Varredura.** Cada agente confere seus PRs abertos pelo menos a cada 60 minutos, a cada acordar do vigia da caixa (AV11) ou, no Codex, na tarefa agendada de hora em hora (AV9), sem lembrete na própria sessão (AV9), só com git, sem gastar API nem Actions: para cada PR, `git merge-tree --write-tree <base atual> <head do PR>`, com a base `origin/main` ou o ramo de baixo da pilha. O relatório diário `prs-parados` (PV (c)) lista os PRs em conflito de todos; o coordenador cobra no canal o dono de cada um.

**Prevenir**

(d) **Arquivos compartilhados.** PR de produto não toca docs/reservations/*, docs/codex-queue.md nem arquivo gerado, salvo quando um teste exige regenerar; nesse caso, regenera pelo script na própria junção. Nenhum PR toca os relatórios de `ON_DEMAND_REPORTS`: são gerados na hora, sem cópia guardada. Em listas e registros que muitos editam (tests/plan-cost-registry.ts, lib/data-families.ts, tests/store-data-registry.ts, inventários de testes, docs/e5-money-readers.md e afins), a linha nova entra na posição em ordem alfabética, nunca no fim do arquivo. O mesmo vale para uma constante nova num registro: ela entra em ordem alfabética do nome entre as vizinhas da mesma seção, nunca logo depois da última constante da seção nem da última linha de uma lista (em 15/11/2026, dois PRs puseram uma constante cada logo depois de `LOCKED_UNTIL_STAR_EXTRA` em tests/plan-cost-registry.ts, e o #3491 entrou em conflito). Aliases de teste: só no arquivo do próprio teste, `tests/aliases/<arquivo>.json`, nunca uma linha nova em `tests/test-config.mjs`, cuja lista antiga não recebe nada (`tests/test-config.mjs`, linhas 4 a 7 e 32).

(e) **Antes de abrir PR e antes de cada push.** Achar, só com git, os PRs abertos que tocam os mesmos arquivos: uma vez por varredura, `git fetch origin '+refs/pull/*/head:refs/pr/*'`, e depois `git diff --name-only origin/main...refs/pr/N` e `git merge-tree` contra a base e contra cada um deles, sem uma chamada da API por PR (AV10 (3)); `gh api .../pulls/N/files` só para os poucos já achados. Se colidir, avisar no canal ("#N colide com #M em <arquivo>"); a ordem entre os dois está em "Depende do dono", abaixo. Em registros de custo (tests/plan-cost-registry.ts, lib/receiving-costs.ts, tabelas de margem), um PR por bloco de cada vez.

(f) **PR pequeno e curto.** Um assunto por PR, de preferência com menos de 400 linhas fora dos testes. O PR que passa 48 horas sem revisão é anunciado no canal para ganhar revisor, porque PR parado é o que mais acumula conflito.

(g) **Pilhas curtas.** No máximo um nível: nenhum PR novo empilhado sobre um PR que já é empilhado. Quando a base entra no main, o empilhado muda a base para `main` na mesma rodada (CV (h)).

(h) **Limite.** O de MV (b), sem mudança: no máximo 15 PRs que dependem do próprio autor (com achado ainda sem correção no head atual, em conflito com a base ou com CI vermelha por causa do próprio código; não contam os que esperam revisão, retorno focal, CI, a fila de merge ou o PR de baixo de uma pilha), com as mesmas exceções (a correção do main vermelho e as correções GRAVE ou ALTO). No limite, como em MV (b), o agente não abre PR novo: revisa PRs dos outros e corrige os achados dos próprios, primeiro os conflitos.

(i) **PRONTO.** "Pronto para fila" só com `git merge-tree` limpo contra o `origin/main` buscado há menos de 1 hora, escrito no próprio aviso junto do head; sem conflito, não se junta o main (MV (c)). Substitui ALL-236 A7 ("merge de origin/main no ramo antes do PRONTO") nesse ponto.

(j) **Base de pilha velha.** A varredura (c) também aponta todo PR cuja base não é `main` e cujo PR de base foi fechado ou está mais de 200 commits atrás do main. Quando a base já entrou ou foi fechada, o autor muda a base para `main`, sem juntar, na mesma rodada. Quando ela continua aberta, o autor junta o main na base e a base no PR só se o `git merge-tree` da base contra o main tiver conflito ou se uma verificação exigida reprovar por causa da idade da base; com `git merge-tree` limpo e verificações verdes, não junta (MV (c)). Em 15/11/2026, #3291, #3678, #3495 e #3073 reprovaram `reservation-check` por bases de 1.700 a 5.000 commits atrás do main.

(k) **PR pronto não envelhece.** Quanto mais tempo um PR fica aberto, mais o main anda e mais conflito ele acumula. Com as revisões exigidas (CV (f)) e as verificações verdes no head, o autor pede `fila #N @sha` na mesma rodada; o enfileiramento segue a torneira em vigor (ALL-236 B), e não um lote do coordenador; com a issue `main-vermelho` aberta (MV (a)), nada é incorporado.

(l) **Teto de custo é recurso compartilhado.** Dois PRs que cabem cada um sozinho no teto do primeiro ano reembolsado do plano Store (US$66, BROADCAST-262; o dólar acima de 65 é folga para qualquer custo honesto até 66, decisão do coordenador 6934185062, opção (a), confirmada em 6935544893) podem passar dele juntos: é um conflito de custo, que o `git merge-tree` não vê. Toda junção do main num PR que muda custo, e todo PRONTO e MERGE WHEN READY, rodam sobre o resultado da junção os testes de teto (`plan-margin`, `read-ceilings`, `email-logo-region`, a seção 11 de `tests/switch-keeps-window.test.ts` e todo teste que use `worstCost`, `netOf` ou o registro de custos), e não só os testes dos arquivos tocados. Se passar do teto, o PR recebe HOLD com o custo mensal da própria linha no Store, e quem corta custo é o PR que ainda não entrou, nunca o que já está no main; a forma do corte, quando muda um fluxo de dinheiro, é decisão do coordenador ou do dono (b). Em 17/11, #4514, #3889, #2571 e #2048 passaram do teto depois da entrada do #2803.

(m) **Push só no head que se juntou e sem outro dono ativo.** Antes de cada push num PR: reler o head (`git ls-remote` ou a API REST) e conferir que é o mesmo sobre o qual o main foi juntado; e conferir, no PR e na issue de coordenação, que nenhuma outra sessão tem CLAIMED ativo sobre ele (das últimas 2 horas, sem UNCLAIMED). Head mudado ou outro dono ativo: não envia; junta de novo a partir do head novo, ou deixa o PR com quem o reivindicou. Uma família com várias sessões (por exemplo, Claude 3 local e as nuvens) envia por uma fila única ou em minutos separados e anunciados, nunca nos mesmos minutos.

(n) **Número fixo em teste compartilhado.** Figura do modelo escrita à mão num teste que muitos PRs mudam (como a seção 11 de `tests/switch-keeps-window.test.ts`) gera conflito a cada junção. Teste novo não fixa número que outro PR pode mudar: confere o limite (acima de zero, abaixo do teto) ou recalcula pelo próprio modelo. Na junção de um teste antigo assim, vale o número que o modelo calcula, com uma nota curta, e as notas dos dois lados ficam.

(o) **Envio automático.** Um roteiro que envia sozinho (fila de envio em segundo plano) tem a condição de minuto testada antes de ser ligado, envia no máximo um PR por vaga, confere (m) antes de cada envio e para no primeiro desvio. Em 17/11, entre 01h32 e 01h41 UTC, uma condição invertida mandou quatro PRs em oito minutos (Claude 3 nuvem R, relatado no #4827).

(p) **Dono antes de preparar a junção.** (m) protege o envio; isto evita o trabalho repetido antes dele. Antes de preparar a junção de um PR, conferir no canal de coordenação em vigor (o de (y): a issue com o rótulo canal-ativo (gh issue list --label canal-ativo), conferida antes de cada escrita) e nos comentários do próprio PR as últimas 6 horas: um CLAIMED, um HOLD, um "re-review needed" ou um push de outra sessão. Havendo, não preparar: a junção é de quem chegou primeiro. Sem dono, publicar o CLAIMED com o head que vai ser juntado antes de começar, e só então juntar. Num agente com várias sessões ou nuvens, a sessão que as coordena divide os PRs e os minutos de envio, e as outras perguntam a ela antes de preparar qualquer PR da família. Em 16 e 17/11/2026, a mesma junção foi preparada duas ou três vezes em ao menos 15 PRs (entre eles #3291, #3171, #3344, #3533, #3568, #3583, #3906, #3928, #3929, #3989, #4135, #4191, #4345, #4522 e #4549). O canal troca de parte sozinho antes de lotar (dono, 20/11/2026): o workflow .github/workflows/coordination-rollover.yml, aos 2.250 comentários da parte ativa, abre a parte seguinte, escreve nela o primeiro comentário explicando a troca, põe a linha "Canal ativo: #N" no topo da parte anterior e passa o rótulo canal-ativo para a nova. Ele nunca fecha issue nem apaga ou edita comentário, com uma única exceção, decidida pelo dono: a 1ª linha do comentário do PAINEL DA FILA (6929670678, na #4827), achado pelo ID e pela marca "PAINEL DA FILA", e só quando essa linha está no formato "#N" ou "Canal ativo: #N"; o resto do comentário fica idêntico, e a linha antiga fica guardada no primeiro comentário da parte nova, para desfazer. Fora do formato, ou sem a marca, ele não edita o painel, mas a troca de parte continua completa, para o canal nunca lotar (dono, 20/11/2026, 18h23): a execução fica marcada como aviso, visível no GitHub, e o primeiro comentário da parte nova diz que o painel não foi atualizado, por quê e qual 1ª linha encontrou, para o coordenador corrigir o painel à mão. Ele só age depois que a variável COORDINATION_ROLLOVER do repositório é ligada; antes disso, a execução à mão só lê e mostra o que faria.

(q) **Pontos quentes dos registros.** Dois lugares concentraram os conflitos repetidos destes dias. Em `lib/redis-memory.ts`, o simulador de scripts do `EVAL` é uma cadeia de `if` independentes: um script novo entra em ordem alfabética do nome que o identifica (`-- marktmorgen:<nome>`), nunca logo depois do bloco do `INCR`, onde todos vinham sendo postos (em 16/11/2026, #3568, #3574, #3583, #4436 e #4568 conflitaram nesse mesmo ponto). Nas listas longas numa linha só (`ELSEWHERE_FAMILIES` e `CLOSING` em `lib/data-families.ts`, `SCOPES` em `tests/plan-cost-registry.ts` e afins), a entrada nova continua na posição alfabética (d); quando a linha onde ela cairia já passa de 200 caracteres, a entrada vai numa linha própria logo depois dela, para que duas adições vizinhas não caiam na mesma linha.

(r) **Conflito na frente da fila do autor.** Um PR em conflito com a base é o primeiro da fila de envio do próprio autor: nenhum PR sem conflito sai antes dele. Depois de cada entrada no main, o autor varre os próprios PRs (c) e reordena a fila na mesma rodada. Exceção: um PR de custo que espera a vez na ordem de custo do coordenador não vai para a frente da fila por conflito só em documentos gerados; ele junta o main na própria vez, num único envio (t). Conflito em código continua aqui e em (a). Em 18/11/2026, o #2048 e o #2287 ficaram cerca de 1 hora em conflito no GitHub, já resolvidos localmente, esperando atrás de envios sem conflito (pedido do dono, 18/11/2026: "PROCURE E RESOLVA TODOS OS SEUS CONFLITOS. CRIE REGRAS PARA NAO CRIAR MAIS CONFLITOS. NAO CRIE MAIS CONFLITOS").

(s) **Junção feita sobre o main da hora do envio.** Uma junção preparada sobre um main só é enviada se, na hora do envio, o main não ganhou depois dela mudança em custo ou em documento gerado (`tests/plan-cost-registry.ts`, `lib/receiving-costs.ts`, a seção 11 de `tests/switch-keeps-window.test.ts`, `docs/limits-proposal*`, `docs/margin-alignment*`, `docs/pricing-*`, `docs/value-presentation*`, `docs/accessibility-inventory.json`), quando o PR também mexe nisso. Se ganhou, junta-se o head do PR com o main da hora num rascunho e rodam-se os geradores: se algum documento mudar, a junção é refeita e os documentos são regenerados pelos scripts antes do envio; se nada mudar, o envio segue sem junção nova (MV (c)). Um `git merge-tree` limpo não basta: um documento gerado desatualizado não dá conflito de texto e só reprova na fila de merge.

(t) **Varredura de deriva depois de um HOTSPOT.** Quando entra no main um PR que muda custo ou documento gerado, o autor de cada PR que também muda custo junta o main num rascunho e roda os geradores no mesmo ciclo, mesmo sem conflito de texto. O PR cujo documento muda é tratado como em conflito (r): junção, regeneração e envio na frente da fila. Um PR de custo que espera a vez na ordem de custo do coordenador só faz a varredura no rascunho, para saber se o documento mudou; a junção, a regeneração e o envio ficam para a vez dele, num único envio, e (r) não o põe na frente da fila antes disso. Em 18/11/2026, 5 de 19 PRs do Claude 3 sem conflito de texto já tinham documentos desatualizados contra o main; em 20/11/2026, seis junções de PRs de custo feitas antes da vez voltaram a conflitar com a entrada seguinte no main antes de serem enviadas (7034160187).

(u) **Nada do próprio PR se perde na junção.** Salvo as notas e os números do bloco tratado em (w), quando um conflito é resolvido pegando o lado do main, inteiro ou por trecho (documentos gerados, a seção 11 de `tests/switch-keeps-window.test.ts`, registros), o autor confere, antes do envio, que cada linha que o próprio PR acrescentou naquele arquivo desde a base comum continua no resultado, por exemplo com `git diff <base comum> <head antigo do PR> -- <arquivo>`, linha por linha. A linha que faltar é reposta, com os números que o modelo calcula agora, num commit próprio da mesma junção. Em 18/11/2026, as 7 notas próprias do #4514 na seção 11 caíram duas vezes em junções do main.

(v) **Uma correção comum, um commit idêntico.** Quando a mesma falha aparece em vários PRs depois de uma entrada no main (CV (e)) e a correção cabe neles, o mesmo diff de código entra em cada um sem nenhuma variação de texto, e o aviso no canal diz o SHA. Assim, quando o primeiro entrar no main, os outros juntam o main sem conflito nesse código, e só os documentos gerados são regenerados (b).

(w) **Número do modelo igual ao do main** (proposta do Claude 3 local, 6967933389). Na junção de um teste com número fixo (n), quando o modelo calcula no resultado da junção exatamente os números do main, o trecho em conflito (os números e as notas daquele bloco) fica com a versão do main, e o PR deixa de tocar nesse bloco; as outras linhas do próprio PR, no mesmo arquivo ou em outro, continuam por (u). As notas do PR sobre junções antigas daquele bloco ficam no histórico do git, não no arquivo. Nesse caso, (w) prevalece sobre o "as notas dos dois lados ficam" de (n). Assim a próxima mudança daqueles números não gera conflito nesse PR.

(x) **Declaração de acessibilidade** (proposta do Claude 3 local, 6967933389). `STATEMENT_REVIEW`, em `lib/accessibility-statement.ts`, é uma linha só, que todo PR com página nova muda. Na junção: ficar com a linha do main; regenerar `docs/accessibility-inventory.json` com `node scripts/accessibility-route-inventory.mjs --write`; pôr a data do dia e o `statementDigest()` calculado sobre o resultado da junção. Nunca marcar uma página como revisada para o teste passar. Em 17 e 18/11/2026, #3838 e #3440 passaram por isso, o #3838 duas vezes na mesma hora.

(y) **Um canal só, conferido antes de escrever.** Antes de cada CLAIMED, envio ou pedido, conferir qual é a issue de coordenação em vigor (a issue com o rótulo canal-ativo (gh issue list --label canal-ativo), e só ela; dono, 20/11/2026, 18h23) e escrever nela. Uma issue que lotou (2.500 comentários) recusa o comentário, e uma que já foi substituída não é lida. Em 18/11/2026, o Claude 3 (nuvem R) escreveu por 13 horas na #4827 depois de a #4848 assumir; o varredor o viu como parado e juntou o main em três PRs dele em dobro.

(z) **Duas bases comuns.** Quando um PR empilhado e a sua base juntaram o main cada um por si, os dois ramos podem ter duas bases comuns (`git merge-base --all <base> HEAD` imprime mais de uma linha). O git junta limpo, mas o GitHub usa uma só base e marca o PR como em conflito (`dirty`), sem rodar a CI; o mesmo vale para um ramo que juntou outro ramo já incorporado ao main. Antes de cada push de um PR empilhado, ou de um que juntou outro ramo, conferir esse comando; com mais de uma linha, juntar a base (ou o main) no PR no mesmo push, mesmo com `git merge-tree` limpo. A árvore costuma sair idêntica (`HEAD^{tree}` igual a `HEAD^1^{tree}`) e o PR passa a ter uma base só. Em 19/11/2026 o #3441 ficou `dirty` sem CI até essa junção (6996428802); o #3511 e o #4573 tinham o mesmo caso.

(aa) **A pilha inteira na mesma onda.** Quando o main ganha mudança em custo ou em documento gerado, o autor junta o main no PR de baixo e, na mesma rodada, a base em cada PR empilhado, de baixo para cima, e envia a pilha em vagas seguidas, a de baixo primeiro. Uma pilha juntada só embaixo deixa os de cima em conflito com o main, que é o que o app do Claude mostra ao dono, mesmo quando eles estão limpos contra a própria base.

(bb) **Resolvido é o que o GitHub mostra.** Pedido do dono, recebido novamente em 20/11/2026, por volta da 00h40 (Fortaleza), à sessão Claude 5 `idD7g`, com o #3402 e o #3395 em conflito no app do Claude: "PROCURE E RESOLVA TODOS OS SEUS CONFLITOS. CRIE REGRAS PARA NAO CRIAR MAIS CONFLITOS. NAO CRIE MAIS CONFLITOS. O CONFLITO DEVE ESTAR RESOLVIDO EM TODOS OS LUGARES, INCLUSIVE, DEVE TAMBEM APARECER COMO RESOLVIDO NO CLAUDE." O começo é o mesmo pedido (Pedidos repetidos, passo 3 (b)); só a última frase é nova, e entra aqui. Uma junção só termina quando, depois do push, o próprio GitHub não mostra mais o conflito: `gh api repos/solrenning-llc/marktmorgen/pulls/N --jq .mergeable_state`, lido pela REST, diferente de `dirty`, que é o estado que o app do Claude mostra ao dono como "Em conflito" (logo depois do push o GitHub pode responder `unknown`; ler de novo até sair dele). Não contam `git merge-tree` limpo na árvore local, uma junção pronta e ainda não enviada, nem um push sobre um main que já andou. "Em todos os lugares" quer dizer: em todos os PRs abertos do autor, não só nos que o dono mostrou; no PR empilhado, contra a própria base e contra o main (aa). O "re-review needed" e o aviso ao dono dizem o `mergeable_state` lido e a hora da leitura.
