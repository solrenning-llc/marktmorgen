## 4a. The bucket lock: what R2 answers (official pages, 8 November 2026)

From https://developers.cloudflare.com/r2/buckets/bucket-locks/ ("Notes") and https://developers.cloudflare.com/r2/api/error-codes/ (code 10069), verbatim where quoted:

- **Delete of a locked object, single-object S3 request (`DeleteObject`)**: "fails with HTTP `409` and the `ObjectLockedByBucketPolicy` error code" (error code **10069**, "Object is protected by a bucket lock rule and cannot be modified or deleted"). The existing object is not modified. This **matches** what #3273 (`claude4/bk1-cron-lock`, `lib/backup-store.ts` `delete`) assumes: a 409 throws `BackupObjectLockedError` and is never a done delete. The error-codes page lists no other 409 for an object delete (`BucketNotEmpty` and `BucketConflict` are bucket operations), so reading any 409 there as the lock is consistent with the page; checking the `ObjectLockedByBucketPolicy` code in the body would be a stricter reading, not a correction.
- **Multi-object delete (`DeleteObjects`)**: "R2 returns HTTP `200` and reports `ObjectLockedByBucketPolicy` for each locked key in the response body". #3273 does not use it; if a later unit switches to it, a 200 must never be read as "all deleted".
- **Write onto a locked name, including a create-only `PutObject` with `If-None-Match: *`**: "The lock check runs before conditions on the object being written, such as `If-None-Match` or `If-Match`, so a write that fails both checks returns `ObjectLockedByBucketPolicy`, not `PreconditionFailed` (`412`)." **This differs from what #3273 says**: `lib/backup-store.ts` (`putNew`, and its header comment "the other is answered 412") expects 412 for a name that already exists; under the lock, a name that exists and is locked answers **409**. #3273's code still throws on it (any status other than 200 or 412 is "Backup write failed"), so nothing is taken as written; only the message and the comment are wrong for that case. Names are random ids, so it needs a collision or a retried write. Not changed by this unit (it belongs to #3273).
- **Lifecycle and lock**: "Bucket lock rules take precedence over lifecycle rules": a locked object is not removed by the lifecycle rule until its lock ends. A bucket cannot be emptied while any lock rule is configured.
- **Billing of a refused request**: a `DeleteObject` is free; whether a `PutObject` refused with 409 is billed is not said (the FAQ bills a 412 and a 400 `BadDigest` as Class A): it is taken as one Class A, inside the rounding million already counted.
- **The Worker (files and videos)** writes into its own buckets through the Workers binding, for which the pages read today do not state the lock's answer: **unknown** until read; the Worker treats any error from a delete or a write as not done.

## 5. The design priced (inbox C4-37, revised by C4-38)

- A **separate Cloudflare account** for backups only, created by the owner; agents never enter it. Three buckets: `marktmorgen-backup` (database), `marktmorgen-files-backup` (files), `marktmorgen-videos-backup` (videos).
- **Database:** the existing Vercel route (`lib/backup-run.ts`), daily copies kept 30 days, plus the first verified copy of each of the 3 newest UTC months (`BACKUP_MONTHLY_COPIES`) in its own folder under `backups/` (C4-36 item 1). A month's copy is at most about 92 days old when the next month's is marked, and **never more than 120 days** (`BACKUP_MAX_COPY_DAYS`). **The bucket's lifecycle rule on `backups/` must be 120 days** (`backupLifecycleDays` on #3293 = the larger of 120 and the retention + 30): it replaces the 30-day rule set on 4 November 2026 (`delete-backups-after-30-days`) and the 60 days (retention + 30) that `docs/backup.md` prerequisite 2 still says on main, which #3293 rewrites to 120. A 30- or 60-day rule would delete the months' copies (the bucket lock ends after 7 days) at 30 or 60 days, and the runbook's step 8.1 (3) relies on them. While the prune is held (the shrink guard), the 120-day rule alone is the cap. Unchanged by C4-38.
- **Files and videos: superseded design.** The C4-37 text (until 8 November 2026, 20:31) had the Worker read the sources "with read-only keys (R2 of the production account and Vercel Blob; Bunny Stream's library read key)". **That is withdrawn and must not be built**: Vercel Blob describes no read-only token (only OIDC inside Vercel and the long-lived `BLOB_READ_WRITE_TOKEN`, which also writes and deletes; private-storage page), and bunny states no read-only key for the Stream API (the library's API key makes and deletes videos; what its `ReadOnlyApiKey` may call is not stated). No production credential (bunny library or account key, Blob read-write token, any R2 key of the production account) is ever put in the backup account.

### 5.1 Files and videos: the pull-through design (C4-38)

1. **A listing route on the site, with its own secret.** A route in this repository (proposed `app/api/backup/source-list`, not built) answers only a call carrying its own secret (proposed `BACKUP_SOURCE_LIST_SECRET`, never `CRON_SECRET` and never any provider key), checked before any other work, and only does two things: it **lists** the sources one page at a time and **signs short-lived read URLs** for what it lists. It never reads, writes or deletes a file's bytes, so the bytes never pass through a Vercel function. Per source:
   - **R2 of the production account:** the route lists with `ListObjectsV2` and presigns `GET` URLs locally (no call to R2; one operation on one object; R2 presigned-URL page). The proposal is that the route signs with an **Object Read only** token scoped to the production bucket, created by the owner for the route alone (R2 tokens page), and never with the site's own read-write key, so that even a bug in the route cannot sign a write or a delete that R2 would accept.
   - **Vercel Blob:** the route lists with the SDK's `list`, then makes **one** `issueSignedToken({ operations: ['get'], pathname: '*', validUntil })` a call (15 minutes; the page allows `*` for the whole store) and signs each listed object with `presignUrl`, which is HMAC-only and needs no network call (Blob signed-URL page, reread 22:55 UTC). The token's `clientSigningToken` never leaves the route: the Worker receives only the per-object `get` URLs, so what it holds is the same as before (a read of one object for minutes). The site's own Blob access stays in Vercel. A `get` URL cannot be used as any other operation. (Signing one token per object, as the earlier text read, would have been up to 1,000 control-API calls a page: Claude 6, MEDIUM 4.)
   - **Bunny Stream:** the route lists the library's videos with the library's API key, which stays in Vercel (it is already there, `BUNNY_STREAM_API_KEY`), and signs each `https://{pull_zone}.b-cdn.net/{video_id}/original` with the **pull zone's URL Token Authentication Key** (proposed `BUNNY_PULL_ZONE_TOKEN_KEY`; the pages do not say it is the embed key that `lib/stream.ts` holds, so it is its own setting). Which of the two token methods (Basic or Advanced) the library's pull zone uses is not known from here: the route must use the one the owner confirms.
   - **Signed lifetimes:** 15 minutes a URL (R2 allows 1 s to 7 days, Blob at most 7 days; bunny takes the expiry the signer sets). A URL that expires mid-copy is asked again on the next part (item 4).
   - **Who holds what:** the route's secret is the **only** thing the backup account holds about production. Whoever steals it can list names and read files (a confidentiality incident: rotate it in both places, incident-response section 8.3), but it **cannot write, overwrite or delete anything**: it never reaches a key, and every URL it obtains is a read of one object for minutes.
   - **The route's own ceiling:** it answers at most the day's planned pages (10 a store per source, three sources, plus 3 a source) and refuses past it, with an alarm; it returns at most 1,000 entries and 1 MB a call. Inside its 10 s it stops signing at an internal cutoff and returns the page so far with a cursor, marked **incomplete**: a slow call never fails a listing silently and never passes as complete. That 1,000 local signatures, one `list` and one token fit in 10 s is **not measured** (no page gives a latency); until it is, a listing that does not finish within the day's pages counts as incomplete (item 2). The deletion records come on their **own** page (from the database, not from the listing), so an incomplete listing never holds them.
2. **Absence is not deletion, and a held deletion has an end.** The Worker never deduces a deletion from an item missing from a listing within 90 days. Deletions come from an **explicit deletion record** that the route returns on its own page (a creator deleted a file, a store closed, a privacy request: the record holds the object's name, the reason and the date, nothing about the person); the Worker keeps every record it receives in the backup account, so a site that later loses or rewrites its records cannot take them back. Each record is applied **30 days after** its date. The guards (proposals of this unit, revised after Claude 6's MEDIUM 2 and 3):
   - **Per day:** a listing that is **empty**, **fails**, is incomplete, or has **more than 20% fewer** objects (or bytes) than the previous complete listing of the same source, or a day whose records would remove more than 20% of a source's objects, **holds every deletion of that source** and fires the alarm.
   - **Cumulative:** the same hold and alarm when the records **received in the last 30 days** add up to more than 20% of the source's objects or bytes (measured against the largest complete listing of those 30 days), or when the complete listing is more than 20% smaller than the complete listing of **7 days** or of **30 days** earlier. A site that sends records for 15–19% of a source each day trips this guard on the second day, not after the copy is drained.
   - **The automatic end:** a held record is applied anyway when it is **90 days** old (proposed `BACKUP_FILES_HOLD_MAX_DAYS`), and the alarm says so every day of the hold, with the date. So erased data with a record leaves the files copies **at most 91 days** after the record (the Worker's daily cycle), inside the 120-day cap, with no manual step. The trade-off, stated plainly: no automatic guard can both keep an erasure deadline and refuse for ever what a compromised site asks; this design keeps the deadline and gives the owner the alarm on every held day, with **at least 60 days** between the start of a hold and the forced deletion (a hold starts no later than the record's 30th day, when it would otherwise be applied, and the end comes on its 90th). The owner's single action, if the alarm shows a compromise, is to pause the Worker's schedule (incident-response 8.1, step 1), which stops every deletion, the forced ones included.
   - **Orphans:** an object missing from **every complete listing for 90 days** without a record is removed after those 90 days (at most 92 days after it left the source: one day to the first listing that misses it, one to the next cycle). The `orphans` alarm (count, bytes and the removal date) sounds the day the orphan is first seen and again at its 90-day end (the day before, and each day it is still kept after that), not on the days in between, so an orphan between its two alarms does not stop the day's heartbeat. An object missing with an explicit deletion record still inside its 30-day wait (or, while the record is held, before its 90-day end) is expected: it is not an orphan, raises no alarm, goes by its record, and the run still sends its heartbeat. A held deletion keeps its `deletions_held` alarm every day, with the date it will be applied. This needs complete listings: a source whose listing never completes (more objects than its pages, item 1 and section 5b) has no orphan end, only its records' end, and stays in the alarm.
   - **Deletions first:** each run applies its due deletions before any copy, so a copy that falls behind never delays a deletion.
   Writing a record from every deletion path in the code is still the code agent's (section 7a); a path that deletes without one leaves an orphan, which the orphan end removes after 90 days of complete listings.
3. **A changed file is a new object.** Same name, new etag: the Worker writes a **new object** in the copy (name from the source's name and the etag) and keeps the previous version **30 days** after it was superseded, then deletes it (a `DeleteObject`, free). A source overwritten with garbage therefore never overwrites the good copy: the good version stays at least 30 days. A day on which more than 20% of a store's objects change etag, or **30 days** in which more than 20% did (cumulative), hold the pruning of that store's earlier versions and fire the alarm (proposal of this unit), so that the owner has time to act; a held earlier version is deleted anyway **90 days** after it was superseded (the same automatic end as item 2).
4a. **A storage ceiling per store that stops copying, never deletes.** Held deletions and held versions would let a store's copy grow past its priced peak. So the Worker keeps, per store, the bytes it holds for it, and before each copy refuses one that would take them past **5 × R** (the peak priced in section 5b, read from the store's plan through the route): the copy falls behind, the alarm fires (proposed reason `files_room`), and nothing is deleted to make room. The storage line of section 5b is therefore bounded by 5R per store in every state, held or not.
4. **Workers Paid, in resumable parts.** Workers Free (10 ms of CPU and 50 subrequests an invocation, limits page, "Last updated Oct 29, 2026") cannot do this. On Workers Paid (minimum $5 a month an account; 10,000 subrequests an invocation; a Cron Trigger of 1 hour or more has 15 min of CPU and 15 min of wall time) the Worker copies in **parts**: each part is fetched from the source with a `Range` request of one part's length and written with the binding's multipart upload, and the state (upload id, part numbers and etags, the source's etag) is written to the backup bucket after each part, so a large video goes on from one run to the next. Before each run's 15 minutes end it stops at a part boundary; a run cut short re-reads at most one part. If the source's etag changed between parts, the upload is aborted (free) and started again as a new version. **Unconfirmed:** whether R2 presigned GETs, Blob presigned GETs and bunny's token-signed pull-zone URLs honor `Range` (no page read says so): until it is shown with a synthetic test against each source's documented behavior, a file larger than one run can move is refused with an alarm, never claimed copied. The Worker never buffers a whole file (128 MB an isolate): as built, it holds one part (at most 5 MiB) in memory to check its exact length before writing it.
5. **The alarm also covers the Worker.** The Worker sends a heartbeat to the external monitor (section 8.7 of docs/incident-response.md) **only on success**: when a full daily cycle (the listings, every pending copy verified, the due deletions) has finished. Silence alarms. The empty, failed, incomplete or shrunk listing and every held deletion with the date it will be applied (item 2, per day and cumulative), the mass etag change (item 3), the per-store storage ceiling (item 4a), a file refused for size (item 4), orphans (the day first seen and at their end, as item 2 says), a copy that falls behind its own ceiling and the route's refusal all alarm too. A stopped Worker deletes nothing: its silence alarms within 26 hours, and every deadline above holds only while it runs.
6. **Privacy timing** (section 7).
7. **Restoring files and videos** creates the source's write access **only at restore time** and removes it at the end (docs/incident-response.md, section 8.3).
