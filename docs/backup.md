## Offline codec and synthetic restore
lib/backup-codec.ts compresses bounded JSON then authenticates it with AES256GCM, fresh96-bit nonce and versioned associated data. Encryption key is supplied in memory; no environment or provider is read. Maximum plaintext4MiB and10000rows are safety limits for this codec, not reduced customer entitlements or a full-export design.
Rows contain a namespaced key, opaque base64 dump and absolute expiry. Decrypt/authenticate before bounded decompression; validate duplicates, schema and expiry; expired rows are excluded at restore time. The codec does not implement Redis DUMP or RESTORE, a consistent export, uploading, retention, git bundles or a production restore.
tests/backup-codec.test.ts restores synthetic rows into an in-memory map and checks byte identity, expiry, corruption, wrong keys and bounds. CI result is pending; no local subprocess tests. This is not a tested real Redis restore and does not count as a production backup.

## Export and synthetic restore (31 October 2026, Claude 2)
Status: built and tested, off. Nothing calls it: no schedule, bucket, credential or encryption key exists, and creating them is the owner's (see the prerequisites above).

`lib/backup-export.ts`, `exportSnapshot`: walks the database with `SCAN … MATCH nl:*`, keeps every key under `nl:`, and copies each with `DUMP` (Redis's own serialized value, any type) and `PEXPIRETIME` (the moment the key ends, as the server has it). `DUMP` answers are binary, so they are read with the REST API's base64 answers (`Upstash-Encoding: base64`, https://upstash.com/docs/redis/features/restapi, read 31 October 2026; `lib/redis.ts`, `redisPipelineBase64`). Upstash bills every command, a script's inside too (https://upstash.com/docs/redis/overall/billing, read the same day). The export checks each `SCAN` against `maxCommands` before sending it, and the whole copy (two commands a key) before sending any `DUMP`. The copy's size is held to `maxBytes`, at most the 4 MiB the codec seals, batch by batch; no batch is sent once it is passed. `maxRows` is at most the codec's 10,000. A cap reached, a cursor that does not move, a key name that came back altered (not UTF-8) or an answer it cannot read is a refusal of the whole, never a partial copy that looks whole. A key gone, or ended, before its copy is left out. It is not a point-in-time copy: a key written during the walk may be in it with its newer value, and a key's value and its end are read in one request but not as one step.

`restoreSnapshot`: writes the rows still alive into a target that has none of the keys; it checks every key first and refuses before writing when one is there. A target's `restore` must never replace a key (`RESTORE` without `REPLACE`, which the server refuses for a key that is there: `BUSYKEY`); that, not the check, is what keeps a key made in between from being written over, and the restore then stops where it is.

Tested (`tests/backup-export.test.ts`, synthetic, 18 checks): every `nl:` key and nothing else, each once, in order; types (string, hash, set, sorted set, list), values and ends back the same after sealing with `lib/backup-codec.ts`, opening and restoring into an empty stand-in database; every command the stand-in receives is recorded, and a budget refusal sends no `DUMP`; a walk in small pages with an empty first page and repeated keys finds every key once; a cursor that does not move is refused; a key deleted between the walk and its copy is left out and the copy still made; the size cap stops at a batch; no restore over an existing key; a restore of nothing asks nothing. Two changes that once went unnoticed (stopping at the first page; checking the budget only after the `DUMP`s) now fail the test. Checked by hand on a real Redis 7.0.15 the same day: `DUMP`, then `RESTORE key <end> <dump> ABSTTL`, bring back every type, including bytes that are not UTF-8, with the same end; `RESTORE` over an existing key is refused (`BUSYKEY`). An independent review the same day measured that one HyperLogLog of ours (the page funnel's and the day's visitors, `PFADD`) dumps to 5–12 KB, so a few hundred of them fill the 4 MiB format: the size cap refuses then, and a larger database needs the format split into parts before this can run.

Still missing, in order: a real restore writer (built since: see "The restore writer" below); the format in parts for a database over 4 MiB; the upload to the backup bucket and its read-back (built since: see "Where a backup is kept" and "The daily run" below); the daily schedule, retention, the two-day failure report (the run and the report's check are built since; the schedule, the retention rule and the report's delivery are not), repository bundles and file copies; and the cost. `SCAN` with `MATCH` walks the whole database, the other products' keys in a shared one too, so a copy costs about 2 × (our keys) + (all keys in the database) ÷ 500 + 1 commands a day at $0.20 per 100,000, with the ceiling set before any is sent; `SCAN`'s count is a hint and its pages can be empty, so the ceiling needs room. Upstash's pay-as-you-go bandwidth is free up to 200 GB a month and $0.03 a GB after (https://upstash.com/pricing/redis, read 31 October 2026). The storage, operations and funding of the backup bucket remain to be reviewed. Unknown is not zero.
## Where a backup is kept (31 October 2026, Claude 2)
Status: built and tested, off. `lib/backup-store.ts`, `backupStoreConfig` and `r2BackupStore`: the store `lib/backup-roundtrip.ts` writes a sealed backup to and reads it back from. It is on only when the owner's own `BACKUP_R2_ACCOUNT_ID`, `BACKUP_R2_BUCKET`, `BACKUP_R2_ACCESS_KEY_ID` and `BACKUP_R2_SECRET_ACCESS_KEY` are set, and never with the sold files' bucket (`R2_BUCKET`) or key id (`R2_ACCESS_KEY_ID`); that check compares names only, so the owner's backup key must be a token scoped to the backup bucket alone. A bucket made under the EU jurisdiction is reached with `BACKUP_R2_JURISDICTION=eu` (https://developers.cloudflare.com/r2/reference/data-location/). Each backup is one object, `backups/<id>.mmbk`, named by the random id the read-back gives it. Every write is create-only: a signed PutObject with `If-None-Match: *`, which R2 evaluates atomically, so of two writes under one name at most one succeeds and the other gets 412, taken as a failure (https://developers.cloudflare.com/r2/api/s3/api/, read 31 October 2026; a 412 is billed as a Class A operation, https://developers.cloudflare.com/r2/pricing/). A read is held to its byte cap as it streams, whether or not the store states a length; a redirect is refused, never followed. Since 4 November 2026 (inbox C4-49) it also lists its own objects under `backups/` (ListObjectsV2, 1,000 names a page, a Class A operation each page; only names it writes, `backups/<uuid>.mmbk`, are offered, and a listing it cannot read whole throws, never reads as an empty bucket) and deletes one by its id (DeleteObject, free on R2; 204 is done, anything else a failure); only the daily run's retention calls them (below). Tested with a stand-in R2 (`tests/backup-store.test.ts`): off without the settings, with the sold files' bucket or key id and with an unknown jurisdiction; the EU address; the write is signed with `If-None-Match` among its signed headers and the body's own hash; a second write under an id is refused and the first kept; a read past its cap is refused, also when the store states no length; a cap that is not a count of bytes, a missing object, an unreachable store and answers of 303, 409 and 503 are refused; the round trip never deletes; the listing, its pages and its refusals (not a listing, truncated with nowhere to go on, a time that is not one, a count that does not match), and a delete of one object by id, an id that is not one refused before any request, a 403 refused. ## The daily run (31 October 2026, Claude 2)

`lib/backup-run.ts` (`runBackup`) joins the pieces: export every `nl:` key under the caps of a reviewed cost ceiling, seal it, write it once to the backup's own bucket under a new name and read it back the same. It never throws: each failure comes back with the step that failed. At most a run and one new try after a failure a UTC day (inbox C4-49): the day's count (`SET … NX EX`, `INCRBY`) is taken before anything costly, a run that ends well raises it past the limit, and every call past it is refused at six commands (the lock, the count, and the lock let go: a compare-and-delete script and the two commands it runs); so at most two sets a day, a failed run's objects included. The walk reads at most `BACKUP_SCAN_PAGES` (200) `SCAN` pages; a walk not done by then is refused as `export_scan_pages` before anything is written, never a partial copy passing as a whole one (inbox C4-46). One run at a time (inbox C4-53): a lock (`nl:backup:lock`, `SET … NX EX`, 15 minutes) is taken before anything else, and a call that finds it is refused as `busy` at two commands (the lock, and `busy` noted as the last failure so a run that did not happen shows in the report), without touching the day's count. The lock holds the run's own random token and is let go only if it still holds it (`lib/redis-lock.ts`), so a run never lets go of a lock another run took after its own ran out. The run writes first and deletes after. (1) Before it writes, it lists every object of its own; when they and one more set at its bound would pass the review's `maxStoredBytes` (or `backupKeptObjects` objects), it deletes the oldest first, never the last verified copy (the manifest kept with the last good copy's time, and the parts it names), and if that deletion fails, or the listing is longer than its pages, it writes nothing (`room_error`, `room_pages`, `room_cutoff`; the day's new try may try again). It deletes to make room only when it knows the last verified copy for sure: a database answer that is not exactly one, a mark that is not the kept shape, an old mark with no manifest, no mark at all while the bucket holds copies, or a manifest the bucket does not list or the run cannot open, and it deletes nothing and writes nothing (`room_unverified`); the mark is kept for good once written, so its absence is a loss, never "no copy yet". (2) Then it writes and, only when the set was verified, deletes every copy of its own older than `retentionDays` days, as best it can: a failure (`prune_error`, `prune_pages`, `prune_cutoff`) is in the report and never costs the day's copy. A failed day deletes nothing after it, so the last good copy stays, past the retention if need be, until a new one is verified; it is one set, so it never keeps the run from making room for the next. Copies are therefore kept up to 30 days, and the last good copy while new ones fail. The ceiling is a proof: no other run writes while one holds the lock, and a run writes only after its own complete listing showed room for its whole set, so the bucket never holds more than `maxStoredBytes`, which `validReview` asks to hold retention + 2 sets (`backupPeakSets`; docs/backup-cost-2026-11-04.md, section 5e). After each run whose deletion finished, none of its own copies (named `backups/<uuid>.mmbk`) is older than the retention; any other name under `backups/` is never deleted by the run, only by the bucket's lifecycle rule, which stays as a safety net. The listing, deletions and copy run under a cutoff of 800 s (`BACKUP_RUN_CUTOFF_MS`, `withCutoff`): no page, part or manifest is begun after it (`export_cutoff`), and the lock outlives it. A review's retention is at least 3 days (`BACKUP_MIN_RETENTION_DAYS`), so the report says no good copy for 48 hours before the last good copy ages out of the retention. The review is read once, from its own data fields (`admitReview`): a figure behind a getter, an inherited review or one that throws when read leaves the run off. Since 4 November 2026 (inbox C4-30) a run copies the keys as a set: sealed parts of at most `PART_MAX_BYTES` each, every one written create-only and read back before the next, and a sealed manifest written last that names every part with its rows, size and SHA-256 (`lib/backup-parts.ts`); a restore reads the set one part at a time, each checked against the manifest (`readBackupSet`), refused past the bytes it may read. The time of the last verified copy and its manifest's id (`nl:backup:last-ok`) and the last failure with its reason (`nl:backup:last-fail`) are kept the longer of 8 days and the retention + 2 days; a later failure never erases the last good copy's time. `backupStale()` is true when no copy has been verified in the last 48 hours, or none is kept.

State: built and tested with the in-memory database and a stand-in bucket only (`tests/backup-run.test.ts`); **off**. It sends nothing until all three exist, each checked before the first command:

1. `BACKUP_COST_REVIEW` in `lib/backup-run.ts`, null today: the owner's review of what one run costs (database commands for the walk, the copy and the run's eight (the lock, the day's count, the last good copy's read and its outcome), one bucket write and one read, the bucket's storage), with its date (YYYY-MM-DD) and source, the days the bucket keeps a copy (`retentionDays`) and the most the kept copies may weigh (`maxStoredBytes`). `validReview` refuses a review without any of them, or whose ceiling is under (retention + 2) × one set's bound (the run writes only below it; inbox C4-53, which replaced the 2 × (retention + 2) of C4-49 and the (retention + 3) of C4-38). The run deletes the copies past the retention itself; the bucket's lifecycle rule is a safety net. Unknown cost is never zero, so without it the run is off.
2. The backup bucket settings (`backupStoreConfig()`, above).
3. `BACKUP_ENCRYPTION_KEY`: base64 of exactly 32 random bytes, kept outside the repository; anything else is no key.

## The restore writer (31 October 2026, Claude 2)

`lib/backup-restore-target.ts` (`restoreTargetConfig`, `backupRestoreTarget`) is the `RestoreTarget` that `restoreSnapshot` writes into: the owner's own, separate and empty Upstash database for restore drills, set by `BACKUP_RESTORE_REDIS_REST_URL` and `BACKUP_RESTORE_REDIS_REST_TOKEN`. It is never the live database: its host is refused when it is the live one's (`UPSTASH_REDIS_REST_URL` or `KV_REST_API_URL`, compared by host whatever the case, port or scheme), its token when it is the live token, and nothing is written unless the target answers `DBSIZE` 0, which the live database never does.

Each row is restored under a temporary name of letters and digits (`POST /restore/<temp>/<ttl>`, the `DUMP` bytes as the raw body, which Upstash appends as the last argument: https://upstash.com/docs/redis/features/restapi, read 31 October 2026), then renamed to its real key with `RENAMENX` in a JSON pipeline, so no real key is ever written in a URL path (how Upstash decodes one is not documented) and no key that is there is replaced. The end is sent as the time still left, from the clock just before sending: approximate, not the exact end the export read. A row whose end passes during the restore is counted apart (`skipped`), never as written.

State: built and tested against a stand-in only (`tests/backup-restore-target.test.ts`); off; nothing calls it. A drill that stops partway leaves the restore database partly filled, and a rerun is refused until it is emptied. Owner prerequisite for a drill: a separate, empty Upstash database and its two settings (never the live database's). Not done: a drill against a real database, which is what will show whether the request form above works there.
