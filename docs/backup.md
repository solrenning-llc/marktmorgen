## Offline codec and synthetic restore
lib/backup-codec.ts compresses bounded JSON then authenticates it with AES256GCM, fresh96-bit nonce and versioned associated data. Encryption key is supplied in memory; no environment or provider is read. Maximum plaintext4MiB and10000rows are safety limits for this codec, not reduced customer entitlements or a full-export design.
Rows contain a namespaced key, opaque base64 dump and absolute expiry. Decrypt/authenticate before bounded decompression; validate duplicates, schema and expiry; expired rows are excluded at restore time. The codec does not implement Redis DUMP or RESTORE, a consistent export, uploading, retention, git bundles or a production restore.
tests/backup-codec.test.ts restores synthetic rows into an in-memory map and checks byte identity, expiry, corruption, wrong keys and bounds. CI result is pending; no local subprocess tests. This is not a tested real Redis restore and does not count as a production backup.

## Export and synthetic restore (31 October 2026, Claude 2)
Status: built and tested, off. Nothing calls it: no schedule, bucket, credential or encryption key exists, and creating them is the owner's (see the prerequisites above).

`lib/backup-export.ts`, `exportSnapshot`: walks the database with `SCAN … MATCH nl:*`, keeps every key under `nl:`, and copies each with `DUMP` (Redis's own serialized value, any type) and `PEXPIRETIME` (the moment the key ends, as the server has it). `DUMP` answers are binary, so they are read with the REST API's base64 answers (`Upstash-Encoding: base64`, https://upstash.com/docs/redis/features/restapi, read 31 October 2026; `lib/redis.ts`, `redisPipelineBase64`). Upstash bills every command, a script's inside too (https://upstash.com/docs/redis/overall/billing, read the same day). The export checks each `SCAN` against `maxCommands` before sending it, and the whole copy (two commands a key) before sending any `DUMP`. The copy's size is held to `maxBytes`, at most the 4 MiB the codec seals, batch by batch; no batch is sent once it is passed. `maxRows` is at most the codec's 10,000. A cap reached, a cursor that does not move, a key name that came back altered (not UTF-8) or an answer it cannot read is a refusal of the whole, never a partial copy that looks whole. A key gone, or ended, before its copy is left out. It is not a point-in-time copy: a key written during the walk may be in it with its newer value, and a key's value and its end are read in one request but not as one step.

`restoreSnapshot`: writes the rows still alive into a target that has none of the keys; it checks every key first and refuses before writing when one is there. A target's `restore` must never replace a key (`RESTORE` without `REPLACE`, which the server refuses for a key that is there: `BUSYKEY`); that, not the check, is what keeps a key made in between from being written over, and the restore then stops where it is.

Tested (`tests/backup-export.test.ts`, synthetic, 18 checks): every `nl:` key and nothing else, each once, in order; types (string, hash, set, sorted set, list), values and ends back the same after sealing with `lib/backup-codec.ts`, opening and restoring into an empty stand-in database; every command the stand-in receives is recorded, and a budget refusal sends no `DUMP`; a walk in small pages with an empty first page and repeated keys finds every key once; a cursor that does not move is refused; a key deleted between the walk and its copy is left out and the copy still made; the size cap stops at a batch; no restore over an existing key; a restore of nothing asks nothing. Two changes that once went unnoticed (stopping at the first page; checking the budget only after the `DUMP`s) now fail the test. Checked by hand on a real Redis 7.0.15 the same day: `DUMP`, then `RESTORE key <end> <dump> ABSTTL`, bring back every type, including bytes that are not UTF-8, with the same end; `RESTORE` over an existing key is refused (`BUSYKEY`). An independent review the same day measured that one HyperLogLog of ours (the page funnel's and the day's visitors, `PFADD`) dumps to 5–12 KB, so a few hundred of them fill the 4 MiB format: the size cap refuses then, and a larger database needs the format split into parts before this can run.

Still missing, in order: a real restore writer (built since: see "The restore writer" below); the format in parts for a database over 4 MiB; the upload to the backup bucket and its read-back (built since: see "Where a backup is kept" and "The daily run" below); the daily schedule, retention, the two-day failure report (the run and the report's check are built since; the schedule, the retention rule and the report's delivery are not), repository bundles and file copies; and the cost. `SCAN` with `MATCH` walks the whole database, the other products' keys in a shared one too, so a copy costs about 2 × (our keys) + (all keys in the database) ÷ 500 + 1 commands a day at $0.20 per 100,000, with the ceiling set before any is sent; `SCAN`'s count is a hint and its pages can be empty, so the ceiling needs room. ## The daily run (31 October 2026, Claude 2)

`lib/backup-run.ts` (`runBackup`) joins the pieces: export every `nl:` key under the caps of a reviewed cost ceiling, seal it, write it once to the backup's own bucket under a new name and read it back the same. It never throws: each failure comes back with the step that failed. At most a run and one new try after a failure a UTC day (inbox C4-49): the day's count (`SET … NX EX`, `INCRBY`) is taken before anything costly, a run that ends well raises it past the limit, and every call past it is refused at six commands (the lock, the count, and the lock let go: a compare-and-delete script and the two commands it runs); so at most two sets a day, a failed run's objects included. The walk reads at most `BACKUP_SCAN_PAGES` (200) `SCAN` pages; a walk not done by then is refused as `export_scan_pages` before anything is written, never a partial copy passing as a whole one (inbox C4-46). One run at a time (inbox C4-53): a lock (`nl:backup:lock`, `SET … NX EX`, 15 minutes) is taken before anything else, and a call that finds it is refused as `busy` at two commands (the lock, and `busy` noted as the last failure so a run that did not happen shows in the report), without touching the day's count. The lock holds the run's own random token and is let go only if it still holds it (`lib/redis-lock.ts`), so a run never lets go of a lock another run took after its own ran out. The run writes first and deletes after. (1) Before it writes, it lists every object of its own; when they and one more set at its bound would pass the review's `maxStoredBytes` (or `backupKeptObjects` objects), it deletes the oldest first, never the last verified copy (the manifest kept with the last good copy's time, and the parts it names; while the prune is held, never a set written before the hold instead, see "Shrink guard" below), and if that deletion fails, or the listing is longer than its pages, it writes nothing (`room_error`, `room_pages`, `room_cutoff`; the day's new try may try again). It deletes to make room only when it knows the last verified copy for sure: a database answer that is not exactly one, a mark that is not the kept shape, an old mark with no manifest, no mark at all while the bucket holds copies, or a manifest it cannot open, and it deletes nothing and writes nothing (`room_unverified`); the mark is kept for good once written, so its absence is a loss, never "no copy yet". When the mark names a manifest the bucket no longer lists (the bucket's rule took it after a long run of failures), the run says "last good copy lost" in the report (`last_good_copy_lost`) and makes room by deleting only objects that no manifest it can open names, keeping every verified set it finds (reading each object small enough to be a manifest, counted as bucket reads); if any of those reads fails, it deletes nothing (`room_unverified`). (2) Then it writes and, only when the set was verified, deletes every copy of its own older than `retentionDays` days, as best it can: a failure (`prune_error`, `prune_pages`, `prune_cutoff`) is in the report and never costs the day's copy. A failed day deletes nothing after it, so the last good copy stays, past the retention if need be, until a new one is verified; it is one set, so it never keeps the run from making room for the next. Copies are therefore kept up to the retention (30 days in the design), and the last good copy while new ones fail; since 8 November 2026 the 3 newest months' copies are also kept, never past 120 days ("Monthly copies" below). The ceiling is a proof: no other run writes while one holds the lock, and a run writes only after its own complete listing showed room for its whole set, so the bucket never holds more than `maxStoredBytes`, which `validReview` asks to hold retention + 2 + 3 sets (`backupPeakSets`, 35 for 30 days, since 8 November 2026; retention + 2 in docs/backup-cost-2026-11-04.md, section 5e, superseded). After each run whose deletion finished, none of its own copies (named `backups/<uuid>.mmbk`, or in a month's folder `backups/monthly/<YYYY-MM>/<run uuid>/` since 8 November 2026) is older than the retention, except the last good copy and the 3 newest months' marked copies, which are kept up to 120 days ("Monthly copies" below); any other name under `backups/` is never deleted by the run, only by the bucket's lifecycle rule, which stays as a safety net. The listing, deletions and copy run under a cutoff of 700 s (`BACKUP_RUN_CUTOFF_MS`, `withCutoff`; 800 s until 8 November 2026, inbox C4-36): no page, part or manifest is begun after it (`export_cutoff`), and the lock outlives it. A review's retention is at least 9 days (`BACKUP_MIN_RETENTION_DAYS`, the bucket lock's 7 days and two, since 9 November 2026; 3 before), so the prune never meets an object the lock still holds, the bucket never outgrows retention + 2 sets, and the report says no good copy for 48 hours before the last good copy ages out of the retention. The review is read once, from its own data fields (`admitReview`): a figure behind a getter, an inherited review or one that throws when read leaves the run off. Since 4 November 2026 (inbox C4-30) a run copies the keys as a set: sealed parts of at most `PART_MAX_BYTES` each, every one written create-only and read back before the next, and a sealed manifest written last that names every part with its rows, size and SHA-256 (`lib/backup-parts.ts`); a restore reads the set one part at a time, each checked against the manifest (`readBackupSet`), refused past the bytes it may read. The time of the last verified copy and its manifest's id (`nl:backup:last-ok`) are kept for good, with no expiry; the last failure with its reason (`nl:backup:last-fail`) is kept the longer of 8 days and the retention + 2 days. A later failure never erases the last good copy's time. `backupStale()` is true when no copy has been verified in the last 48 hours, or none is kept.

State: built and tested with the in-memory database and a stand-in bucket only (`tests/backup-run.test.ts`); **off**. It sends nothing until all three exist, each checked before the first command:

1. `BACKUP_COST_REVIEW` in `lib/backup-run.ts`, null today: the owner's review of what one run costs (database commands for the walk, the copy and the run's own twelve (`BACKUP_RUN_COMMANDS`: the lock, the day's count and its expiry, a paused copy's progress read, the last good copy's read, the outcome with the progress kept or let go, and the lock let go by a script whose GET and DEL are billed one by one; ten until 9 November 2026), one bucket write and one read, the bucket's storage), with its date (YYYY-MM-DD) and source, the days the bucket keeps a copy (`retentionDays`) and the most the kept copies may weigh (`maxStoredBytes`). `validReview` refuses a review without any of them, or whose ceiling is under (retention + 2 + 3) × one set's bound (`backupPeakSets`: 35 sets for a 30-day retention, the 3 newest months' copies included; the run writes only below it; since 8 November 2026, "Monthly copies" below, which replaced the (retention + 2) of C4-53, the 2 × (retention + 2) of C4-49 and the (retention + 3) of C4-38). ## The restore writer (31 October 2026, Claude 2)

`lib/backup-restore-target.ts` (`restoreTargetConfig`, `backupRestoreTarget`) is the `RestoreTarget` that `restoreSnapshot` writes into: the owner's own, separate and empty Upstash database for restore drills, set by `BACKUP_RESTORE_REDIS_REST_URL` and `BACKUP_RESTORE_REDIS_REST_TOKEN`. It is never the live database: its host is refused when it is the live one's (`UPSTASH_REDIS_REST_URL` or `KV_REST_API_URL`, compared by host whatever the case, port or scheme), its token when it is the live token, and nothing is written unless the target answers `DBSIZE` 0, which the live database never does.

Each row is restored under a temporary name of letters and digits (`POST /restore/<temp>/<ttl>`, the `DUMP` bytes as the raw body, which Upstash appends as the last argument: https://upstash.com/docs/redis/features/restapi, read 31 October 2026), then renamed to its real key with `RENAMENX` in a JSON pipeline, so no real key is ever written in a URL path (how Upstash decodes one is not documented) and no key that is there is replaced. The end is sent as the time still left, from the clock just before sending: approximate, not the exact end the export read. A row whose end passes during the restore is counted apart (`skipped`), never as written.

State: built and tested against a stand-in only (`tests/backup-restore-target.test.ts`); off; nothing calls it. A drill that stops partway leaves the restore database partly filled, and a rerun is refused until it is emptied. Owner prerequisite for a drill: a separate, empty Upstash database and its two settings (never the live database's). Not done: a drill against a real database, which is what will show whether the request form above works there.

What the owner sets: a bucket lock rule on the prefix `backups/` of 7 days, shorter than the retention, so the run's own prune never meets it.
- **Shrink guard.** Before the prune, the new copy's keys and bytes are compared with the last good set's (the `base` kept in `nl:backup:last-ok`). A fall of more than 20% (`BACKUP_SHRINK_LIMIT_PERCENT`) deletes nothing (`prune_shrunk`) and keeps the earlier base, so the next days hold the prune too. A mark without a base also deletes nothing (`prune_unverified`) and writes no base. Not built: a way to accept a smaller database as the new base; that is the owner's decision, and until then the alarm keeps failing. Since 9 November 2026 (Claude 2's HIGH and Claude 6's MEDIUMs on #3273): while the prune is held, the mark keeps the moment the hold began (`heldSince`), and step 1 makes room only from the copies written since then, the newest too, never from a set written before it; when those cannot make room (the bucket lock still holds them), nothing is written (`room_shrunk`), so every good set from before the shrink stays until the bucket's lifecycle rule takes it. A mark that could not be read (a failed or misshapen answer) is left as it is, never rewritten without its base, so the next run decides again. With no mark (a first day's try, prune or outcome write that failed once, or a database wiped with its marks), the copy is compared by the same 20% rule with the largest verified set the bucket holds, its keys and its bytes each, read from the manifests (Claude 6's N1, 9 November 2026; the months' copies, kept by name and otherwise not read, are read for it only when no other set is there, and a month's mark with no set that opens deletes nothing): when it fell further, nothing is deleted (`prune_shrunk`) and that set becomes the base, so the hold ends once the database is back to its size; otherwise the copy is the base and the prune runs. A failed try's leftover (no set opens) is no copy. A bucket read that fails then deletes nothing and writes no mark, so the next run decides again; no transient fault leaves the prune held for good. The trade-off of the ceiling (Claude 6's N2): the newest held copy is one of the copies step 1 may delete, so on a rotation day it can go before the day's copy is verified; if that copy then fails, the bucket holds only the pre-shrink sets until a held copy is verified again (up to the lock's 7 days when the failed try's parts are still locked). If the shrink was legitimate (erasures), restoring a pre-shrink set brings the erased data back. Keeping the newest held copy too would stop held copies from rotating until the lifecycle rule frees a slot (retention + 30 days); one more set in the ceiling for the hold is a cost-review change. Both are the owner's decision; neither is built. Step 1 deletes nothing unless the objects it may delete are enough to make room.
- **External alarm (dead-man switch).** `lib/backup-alarm.ts`: after a real run, a sign of life only after a clean success, a failure signal with the reason after `prune_*`, `room_*`, `last_good_copy_lost`, `export_*`, `verify` and `mark_error`, nothing for `off_*`, `busy` and `already_ran`. The monitor raises the alarm on silence: warn after 26 h (`BACKUP_ALARM_WARN_HOURS`), critical after 48 h (`BACKUP_ALARM_CRITICAL_HOURS`). Off without `BACKUP_ALARM_PING_URL` (https, no name, password, fragment or query in it: a failure's `/fail` added to a query would reach the sign of life's path, Claude 5, 9 November 2026); which monitor is the owner's choice, and no account is created here.


## Monthly copies: one retention (8 November 2026, Claude 4)

- **The retention.** Daily copies are kept for the review's `retentionDays` (30 in the design). The first verified copy of each UTC month is also that month's copy, and the copies of the 3 newest months (`BACKUP_MONTHLY_COPIES`) are kept past the retention, about 90 days. No copy is kept past 120 days (`BACKUP_MAX_COPY_DAYS`): a month's copy leaves the 3 newest when the copy of the month three months later is marked, about 90 days after it if that copy is marked early in its month, later if failed or shrunk days delay it, and the bucket's lifecycle rule takes anything older than 120 days whatever the marks say (Claude 6's LOW 3 on #3293). A review whose retention plus its 30 days of lifecycle room would pass 120 days is refused. There are no weekly copies.
- **Which copy is the month's.** It is read from the bucket alone, never from the database. A run whose listing shows no mark for its month (the UTC month of the moment it starts) writes its set under `backups/monthly/<YYYY-MM>/<run uuid>/` instead of `backups/`. After the set is verified and passes the shrink guard, the run writes the folder's mark, an empty `verified.mmbk`, and only then does the set count as the month's copy. A copy that failed, shrank more than 20% or could not be checked never gets a mark; its folder ages out like a daily copy, and the next run that month tries again. If the mark can't be written, the prune deletes nothing that run (`prune_monthly`, which raises the alarm like any `prune_*`). If a month somehow has two marks, the one written first counts.
- **What is never deleted.** Making room and the prune both keep every object in the folders of the 3 newest marked months, along with the last verified copy. The bucket lock and the shrink guard apply as before: nothing younger than the lock is asked for, and nothing at all is deleted after a copy that shrank. Every object in a month's folder sits under `backups/`, so one listing, the one bucket lock on `backups/` and the one lifecycle rule cover them.
- **The ceiling.** The review's `maxStoredBytes` must now hold the retention + 2 + 3 sets at their bound (`backupPeakSets`: 35 for 30 days), and the object count allows a part, the manifest and a mark for each (`backupKeptObjects`). `lib/backup-cost.ts` prices those 35 sets and the mark's Class A write and deletion in every run; the mark is never read back. For the design as built since 9 November 2026 (10,000 keys, 4 MiB in at most two parts: one by size and the part a pause closes; one key a request; 20,212 commands) the worst month at the route's own 800 s (`BACKUP_ROUTE_SECONDS`, held equal to its `maxDuration`) is $29.03 (29,032,329 micro-dollars; $348.39 a year), line by line in "One key a request, a deadline and a resumed copy" below, and every R2 line stays inside the million operations of rounding already counted. It includes the four lines docs/backup-costs-2026-11-08.md (#3271, section 3) priced outside the code until 9 November 2026: Vercel at gru1, its dearest region, one more billing block of each Upstash and Vercel unit, the batch of keys (`BACKUP_DUMP_BATCH`, now one) read before the byte cap refuses it at Upstash's 100 MB record cap read as 100 MiB, and every byte the function moves at Vercel's dearest transfer rate, $0.43 a GB, with the 10% allowance on them. The batch-100 figure (475,490,895 micro-dollars, superseded by the one-key code: $475.49 a month, almost all of it the batch of 100 oversized keys) is no longer the code's, as are the batch-1 estimate of $27.26 (27,257,361, before the pause's part and the progress) and the earlier $10.82 (10,820,417, before the four lines) and $9.36 (9,361,572, at a 300 s route). The company line is still unknown, never zero, while `BACKUP_COST_UNKNOWNS` remain (docs/backup-costs-2026-11-08.md, on #3271).
- **Restore.** A month's copy restores like any other set: its manifest's id is `monthly/<YYYY-MM>/<run>/<uuid>`, and `readBackupSet` reads its parts from the same folder. Offline, download that folder and give `scripts/backup-restore-offline.mjs` the folder and the manifest's own uuid.
- **Keys.** The run reads with the previous key for `BACKUP_KEY_PREVIOUS_DAYS`, which is the 120-day cap itself (`BACKUP_MAX_COPY_DAYS`), so every copy the bucket's rule can still hold opens (decision C1-20261109-0025-C4-47 item 1, 9 November 2026; 60 days before). The run never needs to open the 3 months' copies, because it keeps them by name, but restoring one sealed before a rotation needs the old key. Keep the old key offline for at least 120 days after a rotation. A key rotated because it leaked is the exception ("Previous key for 120 days" below).
- **A create-only write on a locked name.** R2 checks the lock before `If-None-Match`, so a write to a name that exists and is locked gets 409 `ObjectLockedByBucketPolicy`, not 412 (https://developers.cloudflare.com/r2/buckets/bucket-locks/, read 8 November 2026). `putNew` refuses it, and the message names the lock. A 412 is still "already exists". Neither one is ever taken as written.

## One key a request, a deadline and a resumed copy (9 November 2026, Claude 4)

Coordinator's decision C1-20261109-1525-C4-68 (items 2, 3 and 5): the batch stays at one key; measured with the most keys; if a copy does not fit, it stops at a deadline and the next run goes on, the copy marked incomplete until it closes.

- **One key a request.** `BACKUP_DUMP_BATCH` = 1 (100 until 9 November 2026): the copy sends one request (`DUMP` and `PEXPIRETIME`) a key, so at most one key is read past the byte cap. Commands are the same two a key; requests are one a key.
- **The deadline.** No key is begun after `BACKUP_COPY_DEADLINE_MS` = 560 s from the run's start: the 700 s cutoff less `BACKUP_COPY_STOP_ROOM_MS` = 140 s, derived in code from the key request in flight (`REDIS_TIMEOUT_MS`, 5 s), three part closes at the bucket's timeout (`BACKUP_PART_CLOSE_MS` = 2 × `BACKUP_STORE_TIMEOUT_MS` = 40 s each: a part a row overflows into, and the open part closed at the pause or the manifest when the copy ends) and a 15 s margin for sealing and clocks. A key in chunks is begun only when its chunks can close before the deadline; otherwise the copy pauses before it.
- **A paused copy.** At the deadline the open part is closed and read back, and the progress (the last key name handled, every part so far with its rows, size and SHA-256, the counts, the copy's start and its folder) is kept in `nl:backup:progress` for two days at the most. The run is `copy_incomplete`: no manifest, never the last good copy, never verified, never a month's copy, nothing pruned, no sign of life (the monitor's silence is the alarm if it never closes), and the day's count is not raised past its limit, so the day's second run goes on. A pause needs a part left for the rest of the copy: with none (`maxParts` 1), the copy ends as `export_too_many_parts` and nothing is kept.
- **The set window.** A copy's window is the UTC day of its first run. A run of that day reads the progress, checks that every part it names is still listed (or copies afresh), walks the database again and copies only the names after the cursor, into parts sealed with the copy's start, then writes the manifest naming every part; only then is it a set, checked, marked and pruned as before. The first run of a later day leaves the progress (its parts become a failed try's leftovers, aged out by the prune) and starts a new copy, so a copy never spans two days and a daily copy stays daily.
- **Keys that change between the runs.** A key copied before the pause stays in the set as it was copied, even if it is changed or deleted afterwards; a key made after the pause under a name before the cursor is not in this set (the next day's copy has it); after the cursor, each key is copied as it is when its turn comes. A copy was never a point in time; a resumed one spans up to its day.
- **A progress that cannot be read** is never taken as none (rule 24): the run is `resume_unreadable`, writes nothing and lets the progress go, so the day's next run starts afresh. A database answer of the wrong shape is `mark_error`.
- **Measured** (`tests/bk1-resume.test.ts`, synthetic): 9,990 keys of about 410 bytes and the backup's own marks, at the 10,000-key cap; the walk at the 200 `SCAN` pages a shared database may take; every database and bucket request at 0.25 s, the repository's round-trip ceiling (`ROUND_TRIP_SECONDS` in tests/plan-cost-registry.ts, "a review ceiling far above a trip inside one region"), the CPU between them real. A run copies about 2,038 keys before its deadline (561.7 s with the part closed), so the full copy takes 5 runs and about 2,760 s; the CPU is about 0.13 ms a key. With the 2 runs a day (`BACKUP_RUNS_PER_DAY`), a day copies about 4,075 keys, and the copy does not close inside its window at that latency. By the same model, a full copy closes in the day's 2 runs at about 0.107 s a request or less, and in one run at about 0.054 s or less; at batch 100 the same harness closed it in one run of 78 s. Whether it closes is the latency the deployment really has, which no measurement here gives: that, the batch and the runs a day are the coordinator's and the owner's to decide (C4-68 item 3).
- **The worst month at one key a request** (`lib/backup-cost.ts`, `tests/backup-cost.test.ts`, the route's 800 s): R2 storage $0.017306, R2 Class A $4.503510, R2 Class B $0.363295, Upstash commands $2.587264, Upstash bytes $0.245477, Upstash storage $0.000018, Vercel $2.121994, Vercel at gru1 $1.541689, billing blocks $0.719300, the oversized key $0.268436, Vercel transfer $14.024737, the 10% allowance $2.639303: $29.032329 a month. A resumed run is one of the 64 runs a month, each priced at its full caps (a new walk, two listings, the progress read and written at its bound), so resuming adds no run.

## Key id, previous key and the offline tools (8 November 2026, Claude 4)

Inbox C1-20261108-2017-C4-36 items 2, 3 and 7, and C1-20261108-1941-C4-35 item 2. Status: built and tested with synthetic keys and data only; **off**, like the rest.

- **Key id.** Every part (`MMBK2`) and manifest (`MMBM2`) sealed from now on carries its key's id right after the magic: the first 4 bytes of HMAC-SHA256(key, "mm-backup-kid"), bound into the associated data, so a changed id fails authentication. The older formats (`MMBK1`, `MMBM1`, no id) still open. The route's report shows that id as 8 hex (`kid`), never the key.
- **Previous key for 120 days.** After a rotation, `BACKUP_ENCRYPTION_KEY` is the new key, `BACKUP_ENCRYPTION_KEY_PREVIOUS` the old one and `BACKUP_ENCRYPTION_KEY_ROTATED_AT` the rotation day (YYYY-MM-DD, UTC). The old key is used for reading only, from that day until `BACKUP_KEY_PREVIOUS_DAYS` days later, and never if it is malformed or the same as the new key (`backupKeyring`). New copies are always sealed with the current key. Set `BACKUP_ENCRYPTION_KEY_ROTATED_AT` on the same UTC day the key changes (Claude 6's LOW 2 on #3277): without it, or with a later day, copies under the old key do not open, and a run that has to read one to make room stops at `room_unverified`. `BACKUP_KEY_PREVIOUS_DAYS` is `BACKUP_MAX_COPY_DAYS` (120), never a separate figure: the bucket's rule keeps any object up to 120 days, and the run must open every manifest it may still list, or its lost-copy path stops at `room_unverified` and writes nothing (Claude 2's probe A on #3293, now a test in `tests/bk1-monthly.test.ts`). Decided 9 November 2026 (C1-20261109-0025-C4-47 item 1); it was 60 days before.
- **A key that leaked.** When the key is rotated because it leaked (or may have), the owner removes the old key from Vercel at once: delete `BACKUP_ENCRYPTION_KEY_PREVIOUS` (and `BACKUP_ENCRYPTION_KEY_ROTATED_AT`) in the same change that sets the new key, without waiting for the 120 days. From then on, no copy sealed under the old key can be read by the run: not the 3 months' copies, not the daily copies, not the last good copy. Those copies stay in the bucket until the rule takes them at 120 days, and they can be restored only from the offline copy of the old key, which must be treated as exposed. A run that then finds the last good copy lost and an old daily copy it cannot open stops at `room_unverified` (nothing deleted, the alarm fires) until the rule takes that copy; the first copy verified under the new key is the first good one.
- **Lost copy and other keys.** When the last good copy is lost and room has to be made, an object that starts like a manifest but does not open (sealed under a key the run doesn't hold, or damaged) is never counted as "not a manifest". The run deletes nothing (`room_unverified`), because it can't tell which parts that manifest names.
- **Offline tools** (Node's own modules only, no repository or account needed; keep copies next to the offline export):
  - `scripts/backup-restore-offline.mjs <folder> <manifest-id> [--out <file>]`, keys on standard input, one base64 key per line. Without `--out` it only checks, in memory: the manifest opens, every part is present with the size and SHA-256 the manifest lists, and the row counts match. It prints the counts and the key id and writes nothing. That is the monthly check for a real set. With `--out` it writes the rows to one new file, for a restore into a **new, empty** database. Agents' tests only ever write synthetic rows.
  - `scripts/backup-key-fingerprint.mjs < key.txt` prints the 8-hex fingerprint so the owner can check the paper copy and the password manager's copy against the `kid` the offline tool prints for a downloaded set (each object's header carries it). The cron's reply also has it, but Vercel keeps no cron reply, so that is not a report anyone can read later (Claude 2's LOW 1 on #3277). The key is never printed or taken from the command line.

## Keys larger than a part, and the per-key ceiling (9 November 2026, Claude 4)
- **Why:** the key-size inventory of 9 November 2026 found that one key whose DUMP was larger than a part (4 MiB less 1 KiB) refused the whole daily copy as `too_big`, while the affiliate book's snapshot under `nl:aff:` may take 8,000,000 bytes (`lib/affiliate-book-snapshot.ts`, `BOOK_SNAPSHOT_MAX_BYTES`). One large store would have stopped every daily backup.
- **Chunks:** such a key is now copied in chunks over consecutive parts (`lib/backup-parts.ts`). Each chunk carries the key's whole DUMP length and SHA-256; the reader (`readBackupSet`) and the offline tool join them and check order, length, sum and base64 before they hand the key on, so a chunk missing, moved or changed stops the read. A chunk has no `dump` field, so an older reader (`openBackup`, `restoreRows`, an older copy of the offline tool) refuses the part rather than take a piece for a key. **Keep the new copy of `scripts/backup-restore-offline.mjs` beside the export.**
- **Ceiling:** `BACKUP_KEY_MAX_BYTES` (`lib/backup-codec.ts`) is 12 MiB of DUMP: the largest proven writer (8,000,000 bytes) with more than half again for framing. A key over it is never cut short or skipped silently: the run leaves it out, still copies and verifies every other key, and writes a manifest of version 2 that names how many were left out. The run ends as `export_key_over_ceiling` (its own alarm state, with the count in the owner's report): the last good copy's mark stays on the previous complete set and nothing is pruned, so that set is kept. `readBackupSet` refuses a version-2 set unless asked to read it knowingly as incomplete; the offline tool needs `--incomplete` for it and then prints `missing`.
- **Cost:** the stored bytes of one key are now bounded by this ceiling, and every byte DUMP reads, including a key left out, still counts against the review's `maxRunBytes`. The transfer of a key over the ceiling is not bounded by it: DUMP reads the key before its size is known, so that read is still bounded only by Upstash's record size.
- **Base64 checks:** the earlier quad-grouped pattern overflowed V8's regexp stack past about 5 million characters (a DUMP of 4 MB in base64), which made a large key a database `error` before any size check. The backup files now use a linear check (characters, length a multiple of 4, and the round trip).
