# Create-once opportunities from form responses

The reviewed conversion endpoint is POST /api/store/form-opportunity. It requires orders and export access to the pinned store. Creating a new opportunity requires an existing form and a response among the newest 50 shown in Forms. A retry first reads the exact identity-bearing opportunity in that store, so a committed conversion remains recoverable after the response ages out, the form is removed, or the original draft stage or assignee changes. The same shared limit bounds the verification read; this endpoint does not fetch all 2,000 retained responses per click. It never enrolls contacts or sends email.

New public form submissions receive a cryptographically random 128-bit server-generated ID. Submitted fields cannot choose that ID. Storage preserves validated IDs; legacy responses without one keep their original content fingerprint. For new records, the conversion reference fingerprints the store ID, form ID, a response-v1 discriminator and the stored submission ID. For legacy records it fingerprints the original response content as before. The first ten hex characters choose the existing CRM-compatible deal ID; the full 64-character reference is stored on the deal as formResponseRef. A short-ID collision is refused when the full reference differs. Ordinary CRM edits preserve this server-owned field and cannot reassign it from submitted input.

A single-key Lua script checks whether the deal already exists, checks the CRM hash capacity, and performs one HSET only when absent. It returns the existing record on replay without overwriting work done afterward. There is no non-atomic fallback. A lost reply is uncertain; retrying the same conversion uses the same identity. Capacity includes malformed hash entries. Manual CRM saves also recheck capacity and write in a single-key Redis script, so manual creation and form conversion share the same bound under concurrency. Existing records remain editable at capacity. An unavailable script or unconfirmed reply never falls back to an ordinary write.

There is no second receipt table, lock lease or new unbounded history. The existing MAX_DEALS limit is unchanged. A deleted opportunity can be created again from its still-retained response, because deletion removes the identity-bearing record. A response outside this current 50-response conversion window cannot start a new conversion. An existing opportunity can still be recovered through the exact full response reference, without replaying draft changes or reading the response history. Invalid storage replies and identity conflicts fail closed.

## Scope and limitations

- This applies to the new reviewed conversion route, not arbitrary manual opportunities or records created before the feature.
- Legacy response records without a valid server ID still share a conversion identity when identical content arrives in the same second. New public submissions have distinct IDs even for equal content and timestamps. Existing records are not migrated or assigned new identities, so older opportunity links remain stable.
- A repeated HTTP submission is a new event, not automatically deduplicated. This change separates submissions; it does not provide request-level idempotency or exactly-once marketing enrollment. Existing rate limits, consent rules and response retention limits remain in place.
- Returning an existing deal can fail closed if its current stage no longer parses, storage is unavailable or its identity is corrupt. It never replaces the existing record to repair it automatically.
- Two sessions can propose different titles or values for the same response. The first stored record wins. Further edits belong in Deals.
- The existing email-match warning is still useful for other submissions or unrelated sales to the same contact; it is separate from exact conversion identity.

## Verification

The behavior suite uses the project's MemoryRedis test double. Its explicit EVAL branch models this one script and rejects unsupported scripts; it is not a Lua interpreter. Tests cover concurrent requests, lost commit replies, preservation of later CRM edits, server-owned metadata, role checks, capacity, replay at capacity, and collision refusal. The actual application Lua script also passed the disposable Redis 7.4 CI job on 2026-10-16 (run 38930500852, job 117072947744, commit c0e89ec7f90a5cbc65f028cf20da8d392cfc0823). The job verified 64 concurrent requests, replay after a committed request, later-edit preservation, the application capacity limit and wrong-type refusal. It reads the script directly from lib/form-opportunity.ts and requires no application credentials. Hosted Upstash REST integration and authenticated browser verification remain outstanding. No production data or accounts were used.

References: [Redis scripting guarantees](https://redis.io/docs/latest/interact/programmability/eval-intro/), [Upstash EVAL](https://upstash.com/docs/redis/sdks/ts/commands/scripts/eval).

The draft's note copies the response's answers, never an answer that is an email address other than the sender's (a friend's, a referrer's, or any address when the sender cannot be told; lib/form-respondent.ts). A person's erasure deletes the deals that name them as the contact (lib/crm.ts, forgetCrmPerson) and does not read notes, so another person's address must never be copied into one. When the sender cannot be told, the deal has no contact, and each line that held an address stays in the note as "(address not copied)", so the team can see one was given. An address inside a longer answer is kept as typed, as the erasure of form answers keeps it. Deals drafted before this rule may still hold such an address in their note.
