## Achados

### 1. LEVE — `app/studio/page.tsx:1261-1263` com `:851`: uma lista de passkeys não lida faz o passo aparecer como não feito

- **O que o PR promete:** o comentário novo diz "listed only when its tick is known", com a condição `role === "owner" && (recoveryRead !== null || passkeys.length > 0)`.
- **O que acontece:** `passkeys` vem de `listPasskeys(email).catch(() => [])` (`:851`). Quando a leitura da lista falha, ela vira "nenhuma passkey". Se o endereço de recuperação foi lido como vazio (`recoveryRead === ""`), a condição é verdadeira e o passo entra com `done: Boolean("") || 0 > 0 = false`. O criador, que tem uma passkey guardada, vê "Keep a way back in" como pendente, com link para `#account-recovery`. É exibição desonesta (regra 24, VR 2), sem gravação.
- **Contraprova na base:** com o `app/studio/page.tsx` do merge-base `d3bdecde9`, a mesma verificação também falha. O defeito, portanto, é anterior. Mas é exatamente a promessa que este PR acrescenta na sua própria linha, e ela não se cumpre.
- **Correção sugerida:** ler a lista como `null` quando falhar e tratar `null` como desconhecido. Isto é, listar o passo só se (`recoveryRead !== null` **e** a lista foi lida) **ou** se a lista lida não estiver vazia. O convite (`:1358`) e os `PasskeyManager` (`:3454`, `:3544`) precisam do mesmo tratamento (achado 2). Se isso ficar para outra unidade, ao menos estreitar o comentário de `:1261`.
