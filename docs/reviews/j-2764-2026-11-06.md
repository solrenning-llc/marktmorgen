## Result: one MEDIUM, not clean, do not merge

The consent change is present and its original RED is causal. However, both
preview functions accept an unreadable invoice preview as a known zero, and
their real buyer pages then claim nothing is charged today. A subsequent
confirmed switch still sends a charging update with a positive paid invoice.
This is unknown financial evidence becoming a false zero (CX-123 rule24/VR).

Affected boundary: `previewSwitch` in lib/tier-switch.ts and `previewYearly`
in lib/yearly-switch.ts call `dueNow` without validating the preview. The
shared lib/tier-rules.ts helper defaults absent lines to an empty array and
unknown numbers to zero. That helper and the old preview behavior predate
this PR; this is a latent issue in the preview/confirmation boundary touched
by the reviewed switch flows, not a regression introduced by consent.

Reproduction changes only the synthetic GET-like preview response to `{}`
(the actual HTTP operation remains POST /invoices/create_preview). It leaves
the real switches, catalogs, token grant, lock, consent code, page components,
and ordinary positive update response intact. The real preview returns
`ok:true,due:0`; real server rendering contains `nothingToday`. A valid-consent
control then sends exactly one charging update. In these existing fixtures
the paid invoice is $12.40 for the tier and $193.33 for yearly, not zero.
No real provider/account/payment is involved. No arbitrary direct POST,
duplicate payment, or real loss is claimed.

Fix suggestion: validate a complete, bounded preview and its financial fields
before `dueNow` or displaying an amount. An unknown/incomplete preview must
produce an unavailable/retry state with no zero assertion or ready payment
confirmation. Preserve known zero/credit, trial, discounts/taxes, non-digital
classification, and existing paid-work bounds. Do not silently request an
unbounded number of extra pages. Coordinate any shared helper edit with its
owner, or validate within the two owned preview functions.
